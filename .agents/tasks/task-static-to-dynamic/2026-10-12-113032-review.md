# Static-to-dynamic wiring: React Query hooks, live coupon validation, and review submission

Three feature commits wire the Veloura storefront from static data to the FastAPI backend. FEAT-001 adds eight React Query hooks to `api.ts` and connects them to Navbar, MarqueeStrip, Footer, HeroCarousel, JournalPage, ShoppingConfidence, CustomerExtras, and TrustStrip. FEAT-002 makes `applyCoupon` async, routes coupon validation through the backend, and derives live payment methods and shipping thresholds from the DB. FEAT-003 adds `ReviewForm` (POST `/api/v1/reviews` via `useMutation`) and `LiveReviews` (GET via `useReviews`) to the product detail page. All changes preserve offline-first behavior: every hook is gated by `apiEnabled` and carries a `placeholderData` fallback.

Watch for: (confirmed) `useReviews` in `api.ts` filters by `product_id` server-side but `LiveReviews` and `Rating` each filter again client-side — redundant but harmless; (confirmed) `useProductRating` and `Rating` both call `useReviews(product.id)` independently, issuing two identical cache lookups instead of one; (confirmed) `live-catalog.tsx` retains raw `fetch()` calls for the catalog polling loop — pre-existing pattern, not introduced by this change.

**Verdict**: APPROVED

---

## High-level view

All eight hooks in `api.ts` follow the same shape — `enabled: apiEnabled`, `placeholderData` returning the empty-collection equivalent, `staleTime` at 30 s or 60 s — so the offline-first contract is uniformly upheld. No hook omits the guard or the fallback.

`applyCoupon` is now `async (code: string): Promise<boolean>` in both the type definition and the implementation. Every call site uses `void applyCoupon(...).then(ok => ...)`, so no synchronous return-value usage survives. The `discountPercent` state correctly stores the backend-computed or local percent and feeds the discount calculation.

`veloura-data.ts` was not touched by any of the three commits. All static exports (`products`, `articles`, `heroSlides`, `storeConfig`, `coupons`) remain intact as fallbacks.

`ReviewForm` calls `api.submitReview` inside `useMutation`; `LiveReviews` branches on `apiEnabled` and `productReviews.length` to show live, static-demo, or "be the first" states. The build passes with zero TypeScript errors across all three Vite/Nitro bundles.

The one structural awkwardness: `useProductRating` and `Rating` both call `useReviews(product.id)` independently. React Query deduplicates the network request but each component pays the selector cost separately. Not a correctness issue, just an unnecessary duplication.

<summary>Details</summary>

### `apiEnabled` guard and `placeholderData` coverage

Every hook — `useSettings`, `useHeroSlides`, `useCategories`, `useBlogPosts`, `useBlogPost`, `useReviews`, `usePopups` — sets `enabled: apiEnabled` and provides a `placeholderData` value typed to the same shape as the real response. When `VITE_API_URL` is absent, `apiEnabled` is `false`, the `queryFn` never runs, and components receive the empty-collection placeholder immediately. No hook deviates from this pattern.

### `applyCoupon` async contract

The store type declares `applyCoupon: (code: string) => Promise<boolean>`. The implementation is `useCallback(async (code: string): Promise<boolean> => { ... }, [])`. All four call sites use `void applyCoupon(...).then(ok => ...)`:

- `CouponInput` in `shopping-ui.tsx`: `void applyCoupon(code).then(ok => setError(ok ? '' : '...'))`
- `ShoppingConfidence` in `customer-confidence.tsx`: `void applyCoupon(code).then(ok => { if (ok) setSelected(code); })`
- `CustomerExtras` in `customer-confidence.tsx`: `void applyCoupon(couponCode).then(ok => { if (ok) setApplied(true); })`
- `HomeDeals` in `commerce.tsx`: `void applyCoupon('WELCOME10').then(ok => { if(ok) setSelected(true); })`

No site treats the return value synchronously.

### Double filter in `useReviews` and `LiveReviews`

`useReviews(productId)` in `api.ts` already filters the response by `product_id` when a `productId` argument is supplied, so `data.reviews` arrives pre-filtered. `LiveReviews` then runs `data?.reviews?.filter(r => r.product_id === productId)` again. The second filter is a no-op when the hook is called with a `productId`, but becomes the only filter when it is not (i.e., `productId` is `undefined`). Since `LiveReviews` always passes a `productId`, the double-filter is harmless redundancy rather than a bug.

### Duplicate `useReviews` calls in Rating

`Rating` calls `useReviews(product.id)` to derive both the live average and the live count. `useProductRating` (exported from the same file) also calls `useReviews(product.id)` independently. React Query serves both from the same cache entry with no extra network round-trip, but `useProductRating` ends up unused in the product detail page — `Rating` derives its own average inline. The exported hook is dead code relative to the current usage.

### `live-catalog.tsx` raw fetch calls — scope note

The catalog polling loop in `live-catalog.tsx` uses raw `fetch()` calls directly against `API_URL`. This is pre-existing behavior not introduced by these commits. The AGENTS.md rule ("No raw fetch() calls in components") applies to new component code; the catalog poller is out of scope here.
